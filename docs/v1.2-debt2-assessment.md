# debt2 评估：运行时注入机制是否应收敛

日期：2026-11-03。结论：**不做，建议正式关闭此债**。本文为纯评估，不含代码改动。

## 债的原始设想

v1.1 迁移简报第四节「债 2」提出：能力拿运行时信息有三套机制（`bind_tools` / `ContextVar` scope / `state["context"]`），
散落难懂，评估能否「身份统一用类型化 context 承载，减少 ContextVar 特设用法」。简报已预判「会牵动多个能力契约或风险大 → 不做」。

本次把三套机制的**真实调用链**读通后，确认：它们不是三个竞争方案，而是**一条分层数据流 + 一个正交的装配期注入**，各有不可替代的职责与安全含义。

## 三套机制的真实职责

### 1. `bind_tools(tools)` —— 装配期工具表注入（与身份无关，正交）
- `KernelLoop.__init__` 对每个Hook调一次 `bind_tools(dict(self._tool_map))`。
- 唯一消费者 HITL：拿工具表判断某工具是否 `write`（`self.tool_map.get(name).permission`）。
- 一次性、同步、装配期。与「运行时身份传递」完全是两件事，不该被归进同一笔债。

### 2 + 3. `state["context"]` → `ContextVar` —— 同一条数据流的两个阶段
真实数据流是**单向、分层**的：

```
state["context"]  (RuntimeContext：可序列化请求数据，跨进程/跨轮)
      │  Hook before 读取 + 校验 + 派生
      ▼
ContextVar scope  (进程内隐式身份；工具与后续钩子只读)
      │  工具 run 读取
      ▼
工具执行           (工具 schema 故意不含身份字段)
```

- memory：`MemoryWriteHook.before` 从 `state["context"]` 经 `memory_namespace(state)` 校验租户冲突、派生 `Namespace`，写入 `ContextVar`；
  `SearchMemoryTool.run` 和 `after` 只 `scope.get()`；`after` 的 `finally` 里 `set(None)` 防泄漏。
- multiagent：`DelegationHook.before` 同理派生 `AgentContext` 写入 `TurnScope`；`DelegateAgentTool.run` 读 scope 拿身份 + 查委派预算。

## 为什么 ContextVar 不能被 context 取代（三条硬约束）

### A. 安全边界：身份绝不能走工具可见的 state
工具参数（`BaseTool.run(**kwargs)`）**由 LLM 生成**。身份一旦放进工具能读到的地方，LLM 就可能伪造租户/用户。
现状里身份走 ContextVar——**内核/Hook写、工具只读的受信任侧信道**；工具 schema 有意不含身份字段
（`SearchInput`：“Identity and namespaces are intentionally absent from the model schema”）。
把身份挪进 context 让工具读，等于拆掉这道防伪造边界。**这是有意的安全设计，不是技术债。**

### B. 对象身份语义无法序列化
multiagent 的 `TurnScope` 靠 `old.human is human`（HumanMessage **对象身份**）判断「同一用户轮次跨多个模型子轮」，
以此共享一次委派预算。对象身份无法塞进可序列化的 context 而不失真。

### C. 生命周期语义不同
ContextVar 的 set/get/reset(None) 精确对应 before→tool→after 的**进程内轮内窗口**，用完即清。
`state["context"]` 是请求级数据，没有「轮内临时绑定、用完归零」的语义。两者不是一种东西。

## 原始设想为何不可实现

「身份统一进 context」要让工具拿到受信任身份，只能二选一：
- (a) 给 `BaseTool.run` 传 state —— **违反铁律 2（扩展契约不改）**，且身份回到 LLM 可影响的位置，破坏约束 A；
- (b) 保持 ContextVar —— 即现状。

debt1（context 类型化）完成后，`state["context"]` 已是类型化的 `RuntimeContext`，ContextVar 承载的是
「从 context 派生、经Hook校验、工具只读」的身份。两条线职责已清晰分层，**收敛动机已被 debt1 吸收**。

## 建议

1. **正式关闭 debt2**，在 ROADMAP / CONVENTIONS 记为「评估后确认不做」并附本文链接——体现设计克制，而非遗漏。
2. 若将来确有「新增一类运行时信息」的需求，按本文的分层模型落位（可序列化→context；进程内受信任侧信道→ContextVar；装配期→bind_tools），不要试图三合一。
3. 可选的**纯文档**改进（非代码）：在 CONVENTIONS 增一节「运行时信息的三条通道及其边界」，把本文的分层模型固化为约定，供新能力作者参考。这不是 debt2，是文档补全。
