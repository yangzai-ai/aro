# v1.7 业务系统对接：实施前边界提案

日期：2026-11-13。依据：v1.7-business-integration.md、design/CONVENTIONS.md 第 9.7 条。状态：待确认，仅新增提案，未改功能代码。

## 1. 已核对的源码事实

- `api/app.py` 接收 `POST /chat`（兼容 `/api/chat`），JSON 为 message、session_id、target_agent。session_id=null 时创建会话；没有独立创建会话或订阅历史事件接口。
- 服务端没有 SSE id、Last-Event-ID 恢复、事件缓存或请求幂等键。聊天断开会取消当前任务；已经发生的外部写入不一定能撤销。
- 已有 9 种执行事件之外，还在实际发送 session、done、error、approval_required。error 可能 terminal=false，不能一律结束读取。
- `api/sse.py` 按敏感字段名精确忽略大小写匹配脱敏，不是“字段名包含即脱敏”；同时替换已配置密钥值和 URL 用户密码。不是对任意业务文本的完整敏感信息识别。
- tool_result.hook_errors 实际字段为 hook_class、hook、error_type；call_id 不保证 UUID；专家 parent_call_id 可以为 null。正式文档必须以源码为准。
- `TraceHook` 有 get_all_traces/get_latest_trace；HTTP stream_turn 的 finally 只保留最近一条已结束 Trace。会话过期或进程退出后 Trace 不可查询。
- 现有认证是可选的部署级 Bearer token，并无每浏览器用户的 Trace 所有权认证。项目接口使用 X-ARO-Session，但它本身不是额外身份认证。
- 简报标题要求 5 个组件，具体目录和 Props 只定义了 ChatMessage、ThinkingBlock、ToolCallCard、TracePanel 四个组件，以及 useAroChat Hook。

## 2. 冲突一：自动重连不能等同于重发聊天 POST

直接指数退避重发 POST /chat 会重新运行 Agent，可能重复写业务系统。即使尚未收到 session 事件，也不能证明服务端未开始执行。前端无法通过 fetch 网络异常判断请求未到达。

建议本轮：

1. AroClient.chat 只发起一次 POST；断流且无终止事件时抛出结果未知错误，保留已收到的 session/步骤供查询，不自动重放消息。
2. GET Trace 查询允许对网络错误、429、502/503/504 做有上限的指数退避，遵守 AbortSignal；401/403/404 和主动取消不重试。
3. 不把上述查询重试宣传为“聊天断线续传”。真正聊天自动重连需服务端请求幂等、事件序号与重放、任务生命周期协议，另案实施，会触及本轮“事件发送逻辑不改”约束。

需要确认：本轮以“聊天不重放 + 安全查询指数退避”替代简报的聊天自动重连验收；若必须聊天续传，则先单独设计服务端协议，不能在客户端偷偷实现。

## 3. 冲突二：createSession 示例缺少服务端端点

建议保留现有装配：首条 chat 使用 sessionId=null；通过 session 事件取得 ID，并由 useAroChat 管理。target_agent 每次 chat 显式传入，和现有专家会话归属校验一致。tenant_id/user_id 仍由宿主配置设置，客户端不能覆盖。

本轮不新增 POST /sessions，不提供只能伪造 ID 或偷偷发送占位消息的 createSession。SDK 文档展示首条 chat 创建会话的真实流程。若必须保留 createSession(config) 接口，需要另行确认新增会话 API 的装配和身份边界。

## 4. Trace API 最小范围与查询权限

建议在 api/traces.py 增加 router，并在 create_app 注册，core、Engine、TraceHook 不变。

- GET /sessions/{session_id}/traces：返回该活跃会话 Engine 当前保留的已结束 Trace；limit 默认 50、上限 100，offset>=0，按原顺序分页；未知/已过期会话 404。
- GET /traces/{trace_id}：要求 X-ARO-Session 指明会话，仅在该会话 Engine 的已结束 Trace 查找；不存在或属于另一会话均 404，不扫描其他会话。
- 两者使用现有 require_auth；对两者均支持 /api 前缀兼容路由，OpenAPI 主路径保留无前缀版本。
- 响应使用 Pydantic 类型和既有 redact 规则，包含对应 Engine API key 与部署 token 脱敏；不暴露 current_trace 半成品。
- 不删除 stream_turn 的 Trace 截断，不增加另一个无界缓存。因此 HTTP 会话列表通常最多一条，分页仅作用于实际保留记录，不承诺历史审计。
- 部署级 token + 不透明 session ID 不是完整多租户授权。业务代理必须从自身登录态决定允许访问的 session，禁止直接信任浏览器任意透传的 session ID。不得声称本轮新增用户级隔离机制。

需要确认：新增 Trace 请求头要求、只查询当前保留记录的语义，以及注册查询 router 的 API 装配改动。

## 5. 协议与 npm 包方案

协议文档完整记录 9 种执行事件和 4 种已存在的控制/审批事件；未知事件忽略，新增未知字段忽略。明确 reasoning 不能混入正文，不承诺其文本没有业务敏感内容。不引入事件版本字段或实际 Accept 版本协商。

业务代理示例使用 POST + JSON，持有上游连接直到 StreamingResponse 结束；转发状态码、禁止缓冲、传播断连取消，并由代理持有 ARO 密钥。不能采用简报中不存在的 GET stream URL 示例。

packages/client 提供纯 TypeScript 类型、独立 SSE 增量解析、AroClient、审批与 Trace 查询；注入 fetch 便于测试。解析覆盖 UTF-8 分块、CRLF、多行 data、注释、未知事件、非终止 error 和未完成 EOF。

packages/react 提供四个已定义展示组件 + useAroChat；若验收要求第五个展示组件，建议增加 ApprovalCard，复用真实 submitApproval 调用，与现有审批控件语义一致。组件默认无样式，可选 CSS；提供内容渲染插槽以保留工作台的 Markdown 安全渲染，不引入不安全 HTML。

frontend 使用本地包依赖，保持布局/CSS、专家选择、审批、下载、主题、本地历史、reasoning 分段、generation/epoch 和 AbortController 竞态防护。不会将成熟宿主状态全部搬到新 Hook 导致语义重写。通用 Hook 单独提供并独立测试，工作台可继续由既有宿主协调会话与流事件。

需要确认：组件数以“四个展示组件 + Hook”为准，还是采纳 ApprovalCard 作为第五组件。建议采纳 ApprovalCard。

## 6. 发布与验证

按顺序交付协议、Trace API、client、react、工作台。验证包含：原有 427 项保持通过；新增 Trace HTTP 鉴权/跨会话/脱敏/分页/OpenAPI 测试；client 分块解析与查询重试、聊天不重放测试；React 展示和取消/切会话竞态测试；工作台既有测试、TypeScript/build；mypy/ruff。

npm 包先完成 build、测试、pack 与 tarball 消费验证，确保独立于仓库源码可用。真正发布前核实 @aro scope 权限及登录态；不把 npm pack 说成已发布，也不更换包名冒充发布成功。不为此把 npm 凭据写入仓库。

实施完成按用户要求单独提交，不推送 Git、不打 tag；任何 npm 发布缺失均明确列为未完成验收项。

## 7. 待确认的最小决定

1. 聊天断线不自动重发；安全 GET 查询采用有上限指数退避，聊天续传另案。
2. 会话沿用首条 chat 创建，不新增 createSession/POST /sessions，不接受客户端身份覆盖。
3. Trace API 按第 4 节实施，保留现有最近一轮保留策略和部署认证模型。
4. 采用 ApprovalCard 作为第五个展示组件，其余前端提取按第 5 节保持现有语义。

以上确认前停留在提案阶段，不修改生产实现与现有测试，不提交 Git。
