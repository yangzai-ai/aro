# v1.4 工具执行管线加固

> 供 Codex 实现。重约束、轻实现。契约冲突按 CONVENTIONS 9.7 喊停。

日期：2026-11-06。状态：待实施。理由与放弃方案见 [v1.4+ 设计决策](design/decisions-v1.4.md) D4。

## 背景（已核实）

已核对契约与四个中间件子类（Trace、HITL、Memory、Delegation）：**现在没有实际漏洞**，四个子类都不改参数、不改结果。但契约本身有缺口，安全只靠"恰好没人这么写"。插件生态开放前必须收紧契约，先收紧不破坏兼容，等第三方插件依赖了"可以改参数"再收，就会破坏兼容。

缺口清单：
1. 所有 before_tool 共用同一个可变 `tool_args` 字典（`loop.py:197`），执行时用的是这个活对象（`:239`）。审批只给人看副本，执行前不比对（`approval_manager.py:50,63`）。排在 HITL 后面的中间件可以在批准后改参数，用户批准 A 实际执行 B。
2. 中间件顺序由 yml 书写顺序决定，只有 Trace 被强制排在首位（`engine.py:89`）。
3. after_tool 抛异常没有兜底（`loop.py:267`），工具已经执行，后续中间件、tool_result 事件和同批剩余调用全部跳过。
4. ToolResult 可变（`base.py:20`，不是 frozen），Trace、ToolMessage、前端事件三处看到的结果可能不一致。
5. 内核没有统一超时，各工具自行处理。
6. Trace 耗时含审批等待（before_tool 在 HITL 前执行，推断）。

## 要求

**不改钩子签名，收紧语义，由内核强制执行：**

### 1. before_tool 只放行或拒绝

- 内核先把 `tool_call["args"]` 冻结一份（deepcopy），执行时用这份。
- 每个中间件 before_tool 拿到的是副本（再 deepcopy 一份传进去），理论上可以改，但改了也不影响执行。
- 任一个返回 `(False, msg)` 即停，后续中间件不执行，工具不执行。
- 这样中间件排列顺序不再影响安全：HITL 排第几都一样。

### 2. after_tool 只读

- `tool_args` 和 `tool_result` 都传副本（deepcopy），或者改成只读对象（`@dataclass(frozen=True)`）。
- 每个中间件的 after_tool 用 `try/except` 隔离，异常记进 Trace，不影响后续中间件、tool_result 事件和同批剩余调用。
- ToolMessage 已经在 after_tool 之前生成，不受影响（现状 `loop.py:266`）。

### 3. 内核统一超时

- BaseTool 增加 `timeout_seconds: float | None` 可选属性（默认 None）。
- 内核用 `asyncio.timeout(tool.timeout_seconds)` 包裹 `tool.run`，只计执行时间，不含审批等待。
- 超时转成失败 ToolResult，继续执行同批剩余调用。
- **不做通用重试**：写操作大多不能安全重放。工具自己需要重试的，仍可以在 run 里实现。

### 4. Trace 分离授权与执行耗时

- before_tool 记 `approval_start`，审批通过后记 `approval_end`，工具执行前记 `exec_start`，执行后记 `exec_end`。
- ToolStep 增加两个字段：`approval_duration_ms: float | None`、`execution_duration_ms: float`。原有 `duration_ms` 保留为总耗时兼容。
- 未走审批时 `approval_duration_ms` 为 None。

### 5. CONVENTIONS 硬约束

- 在 `docs/design/CONVENTIONS.md` 第 5 节（中间件钩子）增加明确规则：
  - before_tool 只能放行或拒绝，不得修改 tool_args 影响执行。
  - after_tool 只读观察，不得修改 tool_args、tool_result 或 state.messages。
- after_tool 可以写 state.context 或外部存储（Memory 中间件就这么做），不算违规。

### 6. 恶意中间件测试

新建 `tests/core/kernel/test_malicious_middleware.py`：

- 实现一个恶意中间件：before_tool 改 tool_args、after_tool 改 result 字段、after_tool 抛异常。
- 注册它，排在 Trace 之后、HITL 之前 或 HITL 之后（都测）。
- 断言：
  - 实际执行的参数是原始参数（恶意中间件的改动被隔离）。
  - Trace 记录的结果是真实结果（不是恶意改写后的）。
  - after_tool 的异常被捕获且记进 Trace，其他中间件和 tool_result 事件照常执行。
- 同批多个工具调用时，一个抛异常不阻断另一个。

## 不改的部分

- 钩子签名不变：`before_tool(tool_name, tool_args, state) -> tuple[bool, str | None]`、`after_tool(tool_name, tool_args, tool_result, state) -> AgentState`。
- 四个现有中间件不用改实现，它们本来就守规矩。
- 中间件注册顺序仍由配置决定，Trace 仍强制排首位，不新增阶段。
