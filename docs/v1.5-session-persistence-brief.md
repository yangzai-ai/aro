# v1.5 会话持久化

> 供 Codex 实现。可配置按需开启。核心是 Session 存储接口，不只是 Checkpointer 替换。

日期：2026-11-09。状态：待实施。理由与放弃方案见 [v1.4+ 设计决策](design/decisions-v1.4.md) D2。前置：v1.4 管线加固（031165f）。

## 背景

现状：会话在进程内存字典（`api/sessions.py:62`），重启或超过 TTL 全部丢失。LangGraph checkpointer 是 MemorySaver。

决定：持久化的对象是 **Session**（消息+元数据），不只是 checkpoint 快照。内核定义中立存储接口，三种实现：内存（默认）、SQLite（单机）、PostgreSQL（企业）。按需启用，环境变量或配置文件指定。

## 设计

### 1. 中立存储接口

新建 `core/kernel/session_store.py`，定义 `SessionStore` 协议（或抽象基类）：

```python
class SessionStore(Protocol):
    """Session persistence layer, independent of database choice."""
    
    async def save(self, session: Session) -> None:
        """Persist session (messages, metadata, state). All-or-nothing."""
    
    async def load(self, session_id: str) -> Session | None:
        """Restore session by ID. Return None if not found or expired."""
    
    async def delete(self, session_id: str) -> None:
        """Delete session. Idempotent."""
    
    async def list_active(self, max_age_seconds: int) -> list[str]:
        """List unexpired session IDs (for cleanup)."""
    
    async def close(self) -> None:
        """Cleanup resources (DB connection pools, etc.)."""
```

方法必须是幂等的（同个 session_id 重复 save 不出错，delete 不存在的不出错）。

### 2. 三种实现

**2a. InMemorySessionStore（默认）**
- 现有 `api/sessions.py` 的字典逻辑，包装成符合协议的类
- 无外部依赖，开发/测试零成本
- 内存 TTL 机制保留（活跃会话驻留多久）

**2b. SqliteSessionStore**
- SQLite 文件数据库（`.aro/sessions.db`）
- 依赖：仅标准库 `sqlite3` 或 `aiosqlite`（异步）
- 表结构：session_id, engine_id, target_agent, tenant_id, user_id, created_at, updated_at, expires_at, state_json, checkpoints_json
- 索引：session_id（主键）、expires_at（清理查询）
- 启用：`ARO_SESSION_STORE=sqlite` 或配置文件 `session_store: sqlite`

**2c. PostgresSessionStore**
- 表同上，连接池化
- 依赖：`asyncpg` 或 `psycopg` 异步驱动
- 启用：`ARO_SESSION_STORE=postgres` + `ARO_DB_URL=postgres://...`

### 3. Session 序列化

Session 是复杂对象，包含：
- 消息列表（`state["messages"]`）：HumanMessage、AIMessage、ToolMessage，各含 tool_calls、additional_kwargs（reasoning_content）
- 元数据：target_agent、租户、用户身份、时间戳
- 活跃标志和 Checkpointer 快照

**序列化方案**：
- 消息用 LangChain 的 `to_json()` / `from_json()`（内置序列化）
- 元数据用 Pydantic model 序列化
- Checkpointer 快照（GraphState）用同方式保存
- 整个 Session 转 JSON 或 msgpack，存数据库或磁盘

关键：reasoning_content 必须完整保留，恢复后模型能用。

### 4. 会话生命周期

**创建**：
- 新建 Session 对象，分配 UUID session_id
- 还在内存字典里。

**更新**：
- 每轮执行后，状态一致时 `await store.save(session)`
- 包括消息列表、工具结果、Trace、事件流状态

**恢复**：
- 请求带 session_id 进来
- 内存字典里找不到，`await store.load(session_id)`
- 加载失败（Not Found 或过期）返回 404，用户建新会话
- 加载成功，重建引擎并继续

**关闭**：
- 显式 DELETE 请求 → `await store.delete(session_id)` + 内存清理
- 到期自动删除：后台定时任务跑 `store.list_active()` 找过期的，调 delete

**悬空调用补结果**（恢复时）：
- 加载的消息列表可能有"工具调用"但没"工具结果"，说明在重启前挂起
- 补一条 ToolMessage：`content="因服务重启未执行"`，`tool_call_id` 引用这个调用
- 模型知道这个工具没执行，不会重复

### 5. TTL 分层

- **内存 TTL**（`settings.session_ttl_seconds`，默认 3600）：会话在内存字典里驻留多久。过期自动从内存清掉，但存储里仍然有。
- **存储保留期**（`settings.session_retention_days`，默认 30）：存储里的会话最多保留多久。到期真删。

两个 TTL 允许在内存里常驻热会话，又不无限占用磁盘。

### 6. 配置

在 `api/settings.py` 增加：

```python
session_store_type: str = Field(
    default="memory", 
    enum=["memory", "sqlite", "postgres"],
    description="Session persistence backend"
)
session_store_path: str | None = Field(
    default=None,
    description="For sqlite: file path (default ~/.aro/sessions.db)"
)
db_url: str | None = Field(
    default=None,
    description="For postgres: connection string (ASYNC driver)"
)
session_ttl_seconds: float = Field(default=3600)
session_retention_days: int = Field(default=30)
```

环境变量映射：
- `ARO_SESSION_STORE_TYPE` → session_store_type
- `ARO_SESSION_STORE_PATH` → session_store_path
- `ARO_DB_URL` → db_url

### 7. 集成点

**api/app.py**：
- 启动时，根据配置创建对应的 SessionStore 实例
- 注入给 SessionStore 使用
- 关闭时调 `await store.close()`

**api/sessions.py (SessionStore 类)**：
- 构造时接收存储后端实例 `backend: SessionStore`
- load 先查内存字典，没有调 `backend.load()`
- save 时同时更新内存字典和调 `backend.save()`
- 后台定时任务（asyncio.Task）清理过期会话

**内核不改**：loop.py、engine.py、checkpointer.py 保持原样。Checkpointer 仍是 LangGraph 的快照，但现在整个 Session 被上层存储了。

## 不改的部分

- 审批 Future 机制不改（D3 暂不改 interrupt）
- Engine 类不改（checkpointer 仍注入，但现在由更上层的 Session 存储管理）
- Middleware 和工具执行不改
