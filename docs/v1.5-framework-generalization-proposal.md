# v1.5 框架通用化：源码核对与最小装配提案

日期：2026-11-10。状态：待确认，未改功能代码。

依据：v1.5-framework-generalization.md、design/CONVENTIONS.md 第 0/2/9.7 节与 design/decisions-v1.4.md D2。

## 需要确认的差异

1. 简报的 discover_capabilities() 示例实例化全部 entry point，而现有 Engine 明确保证仅加载配置启用的能力。全量实例化会让安装包自动获得执行/资源初始化机会，也破坏禁用不导入测试。
2. AgentConfig 目前只接受 capabilities 字符串列表 + capability_config；简报另给 capabilities 映射格式。两种写法需要归一化，不能直接把映射交给现有 loader。
3. Hook 目前为 ABC（before/after 抽象方法），不是 Protocol；现有同步 Engine 构造也无法 await on_start。直接把示例 Protocol 替换进去或在构造器运行事件循环都会改变既有兼容性。
4. api/sessions.py 实际存在审批和专家的具体依赖：ApprovalManager/HITLCapability、MultiAgentCapability、LocalAgentHandle、AgentDescription（含运行时与 TYPE_CHECKING 导入）。没有 api/trace.py；TraceHook 已在 core/kernel，无需另造 TraceService。
5. on_session_load 能替换 AgentState，必须防止覆盖请求的 thread_id/tenant_id/user_id。当前 API 在 SessionStore.reserve 中生成身份，Engine.run 没有独立 session_id 参数。
6. 简报“core 内部可以引用 capabilities”与现行依赖方向冲突。本提案继续禁止 core 导入具体能力，不采用这条例外。

## 建议实施口径

### 1. Entry Point：发现元数据，按配置启用

- 新增 discovery.py，组名 aro.capabilities。公共无参 discover_capabilities() 支持简报要求的独立发现；Engine 使用同一发现入口的可选名称/配置过滤参数，只加载明确启用的条目，不因安装而自动启用。
- Engine.__init__/create 增加可选 capabilities 参数；显式列表（包括 []）优先，跳过配置发现。默认仍按 YAML 配置顺序启用，不把发现顺序当装配顺序。
- 优先级：显式对象列表 > 显式 module 配置 > 同名 entry point > 既有模块约定回退。显式选中 entry point 加载失败必须失败关闭，不能静默回退到另一个同名插件；独立发现中单个损坏插件只记插件名/异常类型，继续其他条目。
- 类入口使用无参构造后 initialize(config)，沿用 Capability 已有契约；不改 Capability 基类、不猜测任意构造器。需要特殊构造的插件可提供符合文档约定的配置工厂，具体调用约定在实现前固定，不用捕获 TypeError 反复试调用。
- AgentConfig 兼容 capabilities 列表与映射。映射归一化到现有 names/config 视图；若同名同时出现在两处配置则明确拒绝，避免隐式覆盖。
- 已加载对象立即登记进 Engine 资源所有权列表，后续发现/启动失败时沿现有回滚清理，避免批次失败导致先前实例泄漏。

### 2. Hook：保留 ABC，增加四个默认无操作方法

- 保留现有 before/after/before_tool/after_tool/bind_tools 的实现和调用顺序；只添加 on_start/on_session_load/on_session_close/on_stop 默认方法，on_session_load 默认 None。调用边界按简报使用 hasattr 兼容。
- create() 在能力启动并装配后 await on_start；同步构造保持可用，在首次 run 或显式异步生命周期入口启动 Hook，第一轮前完成。每个 Engine 一次；启动失败回滚已进入启动的 Hook，on_stop 与能力 close 不互相替代。
- on_start 收归一化的 Agent 配置副本，不传 LLMConfig/API 密钥；close 在资源释放前逆序尝试 on_stop，单个失败/取消不跳过剩余 Hook、能力、LLM 和检查点清理，沿用现有 shield 清理语义。
- Engine 增加显式会话加载/关闭方法供宿主调用；run 在新增用户消息和 Trace.start 前执行加载，使用调用方 state.context.thread_id（缺失时生成），不改 run 签名、不改图主循环。
- 按 Hook 顺序取第一个非 None 的恢复状态，其余不调用；加载发生在每次 Engine.run 的用户轮开始，不在每个图内工具轮重复恢复。恢复必须先校验状态结构与身份，缺少身份时注入调用方身份，已存在的身份冲突则拒绝，不能覆盖宿主身份；当前用户输入只追加一次。
- SessionStore 关闭链（DELETE/过期/服务退出）在取消在途请求后通知 on_session_close，再释放专家 scope 或 Engine；同一关闭任务只通知一次。CLI/嵌套 Engine 的活跃会话也由 Engine.close 收尾，去重通知。停止不会触发自动工具重放。

### 3. API：中立服务协议，项目层负责具体适配

- 不新增 TraceService：API 当前已从内核 TraceHook 读取数据，额外协议无收益。
- 在 core/kernel 定义最小、类型化的审批与本地专家目录服务协议（只表达现有 API 真正使用的操作），以及 Hook 可选 provides 映射的读取边界。它们是 Hook 暴露宿主服务的类型描述，不是新插件组或第三个扩展点；与 D2 的 provides 方向一致。
- api 只依赖这些协议与 Engine/Capability，不通过字符串类名或 Any/getattr 链绕开边界。删除 TYPE_CHECKING 中的具体能力导入。
- Helpdesk 项目层适配现有 HITL/专家能力，保留无会话专家目录、延迟启动专家、只读检查、审批 mode=api 校验、会话归属/容量/互斥/取消语义；现有四个 Hook 的逻辑不动。目录适配不能先启动所有专家或加载知识权重。
- 通用 api 的默认装配不隐式导入项目适配；projects/helpdesk/api.py 显式组合。需要的可选宿主装配参数会保持现有 create_app/SessionStore 调用兼容。测试使用既有工厂时以相同中立服务接口接入，不降安全断言。

## 拟改动范围与不改范围

预计涉及 discovery.py、hook.py、engine.py、config_loader.py、API 会话/装配与少量项目适配、测试及说明。新增服务类型放 core/kernel，具体适配放 projects/helpdesk。

不改 BaseTool、Capability 基类、图执行流程和四个现有 Hook 的逻辑；不实现持久化插件，不引入新依赖，不放宽内核对具体能力零认知。

## 验证计划

按任务顺序实施。发现至少 3 项测试、生命周期至少 5 项测试，另覆盖禁用不导入、显式对象优先/空列表、配置兼容、加载失败回滚、恢复身份冲突、并发启动/关闭取消清理，以及 api AST 禁止具体能力导入。

既有 317 项测试全部保留并通过；mypy=0、ruff=0，必要时复核前端构建和既有 API 路径。最终单独提交 refactor: v1.5 框架通用化 后暂停复验。

## 本次暂停原因

这不是因为工作量而暂停：插件激活规则、配置语法、Engine 生命周期入口和 API 服务装配均触及既有契约/装配。简报授权了目标，但示例与现有保证存在上述差异。按 CONVENTIONS 9.7 先提交可审阅方案，确认口径后实施，不自行放宽安全与可插拔边界。
