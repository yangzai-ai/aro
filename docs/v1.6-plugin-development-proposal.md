# v1.6 会话持久化：实施前冲突与最小提案

日期：2026-11-11。核对基线：49aeeda（包含 v1.5 c77f377）。状态：待确认；未修改功能代码。

依据：v1.6-plugin-development.md、CONVENTIONS 9.7、当前 Engine/Hook/Capability 源码。

## 1. 指定的 get_thread_id 入口实际不存在

源码无 core/kernel/context.py，也没有 get_thread_id。v1.5 只有 state.context.thread_id 与 runtime_context(state) 访问入口，前轮并未交付简报假定存在的 ContextVar API。

建议批准一个限定框架补修：增加 core/kernel/context.py，提供 get_thread_id() 和内核使用的作用域绑定上下文管理器；Engine 在校验/恢复状态后、调用图之前绑定 thread_id，在 finally 中 reset。沿用图已有 copy_context 传播，不改图节点、工具或旧 Hook。并发 Engine、嵌套委派、失败/取消时必须覆盖身份不串用与清零测试。插件严格通过 get_thread_id() 获取保存键。

替代方案为插件在 before 内自行绑定，但仍需新增 core 入口，而且生命周期所有权散落在插件；不建议。

## 2. 删除语义与“正常关闭重启恢复”互相冲突

当前 Engine.close 会对所有活跃会话调用 on_session_close；API DELETE、过期、服务退出也都使用相同通知。若插件无条件 delete，关闭 Engine 后数据库记录被删，“关闭 Engine，重新创建，再加载”验收必然失败。

为守住“不改框架生命周期语义”，建议本轮插件增加 delete_on_session_close: bool = False：

- 默认 on_session_close 不删除持久化记录，on_stop 仅释放连接；数据由 retention_days 过期策略清理，支持正常关闭后恢复。
- 显式设 True 时执行 backend.delete，兼容简报删除示例，但明确不支持该配置下正常关闭后的恢复。
- backend.delete 保留独立幂等操作供将来删除入口使用。
- 默认模式下，工作台“关闭会话”表示结束运行会话，不等于从数据库永久删除；本轮不宣传具有单独永久删除接口。

如果必须同时做到“DELETE 立即永久删除”和“服务退出保留”，需区分销毁/卸载事件或增加关闭原因；这涉及框架生命周期/宿主契约，应另行批准，不能由插件猜测退出原因。

## 3. async initialize 示例与已有 Capability 契约不一致

Capability.initialize 是同步配置方法，Capability.start/close 才是异步方法。无需改契约：插件 initialize 只校验配置并构造尚未连接的 backend；Hook.on_start 初始化 backend，Hook.on_stop 关闭；Capability.close 仅作启动未进入 Hook 等失败路径的幂等兜底。backend 初始化/关闭必须幂等，避免重复连接/关闭。旧 Hook 不改。

## 4. 悬空调用不能声称一定“未执行”

崩溃可能发生在外部写入成功后、保存结果之前。恢复时没有 ToolMessage 只证明“未记录结果”，无法证明没有执行。

建议补 ToolMessage 的安全文案为：“因服务中断，此工具调用未记录结果，执行状态未知；未自动重放，请先查询业务系统核实。”绝不自动重新执行工具。

补结果必须放在对应 AI 工具调用批次结束处、下一条非 ToolMessage 之前，不能一律追加到整段历史末尾；保留已有结果、同批顺序以及 reasoning_content/tool_calls，不伪造成功。对格式歧义（缺 ID/同批重复 ID/无法关联的结果）明确拒绝，不猜配对。

## 5. 宿主恢复边界

当前 API 对不存在的 session_id 返回 404，只在新会话生成新的随机 ID。插件无法在不改 API 会话装配的情况下，让浏览器拿旧 ID 重启续聊。

建议本轮集成验收限定为：使用受信任调用方提供的 state.context.thread_id 重建 Engine 并恢复，数据库持久化可跨进程验证；不宣传浏览器跨重启续聊。该产品路径如必须包含，需要再扩展宿主装配（鉴权后恢复旧 ID），不是插件自行把 404 放开。

## 实施范围（以上口径确认后）

- 完整实现 Memory/SQLite/PostgreSQL backend 协议，默认 memory；SQLite 与 asyncpg 依赖按需导入，增加可选依赖组，不因未启用插件加载驱动。
- LangChain 内置 messages_to_dict/messages_from_dict；保存 context 与顶层 tenant_id，身份冲突继续由 v1.5 校验，插件不重复身份校验。
- retention_days 控制 load 过期与初始化时过期清理；数据库使用参数化查询、幂等建表/upsert/delete，SQLite 路径可配置，PostgreSQL URL 仅来自 ARO_DB_URL，错误不泄露连接串。
- 至少 10 项测试，覆盖三 backend、序列化、悬空批次补齐、TTL、资源关闭/取消、框架身份拒绝、Engine 重建恢复与 backend 配置选择。没有真实 PostgreSQL 服务时明确区分协议模拟测试与真实数据库证据，不虚报联调。
- 不做可选能力包装和权限清单：既有 HITL/Memory/Delegation 已是 Capability；新增 Trace 包装与权限执行会扩展本次边界。
- 除第 1 项批准的通用上下文入口与绑定外，不改 BaseTool、Capability 基类、图执行流程、旧 Hook 逻辑。
